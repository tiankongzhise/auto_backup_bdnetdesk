# Design：pywebview 前端设计规范

## 设计目标

前端是面向普通 Windows 用户的工作台，不是工程状态浏览器。它必须帮助用户快速判断：

- 当前是否已授权。
- 当前能不能开始备份。
- 最近任务卡在哪一步。
- 是否存在同步、远端校对、缓存、清理或恢复风险。
- 下一步应该点哪个按钮。

设计不追求装饰感。界面应安静、密集、清楚、可扫描，适合反复使用。

## 信息架构

主窗口采用左侧导航、顶部状态栏、右侧主工作区。

| 页面 | 角色 | 必须回答的问题 |
| --- | --- | --- |
| 工作台 | 默认首页 | 当前是否可备份，下一步做什么，有哪些风险。 |
| 备份 | 创建和继续任务 | 备份哪些来源，任务状态是什么，能否开始/继续。 |
| 百度授权 | 授权与 token 自检 | 当前设备使用哪个百度账号，本机能否解密 token。 |
| 恢复 | 来源级恢复 | 哪些来源可恢复，恢复到哪里，是否需要远端下载。 |
| 清理 | 原始数据清理 | 哪些来源可安全清理，清理方式是什么。 |
| 校对与同步 | 一致性检查 | 本地、云端、百度远端是否一致，如何人工处理。 |
| 设置 | 参数与诊断 | 缓存、上传、版本、WebView2 和发布候选诊断。 |

## 页面规范

### 工作台

必须包含：

- 设备摘要、百度账号、云端状态、缓存状态。
- 一个主下一步动作，最多两个次动作。
- 最近任务列表。
- 风险提醒列表。
- 运行中操作条。

主动作优先级：

1. 未授权：完成百度授权。
2. 无任务：添加来源并创建备份。
3. 有可继续任务：继续任务。
4. 有可恢复记录：做一次恢复演练。
5. 有校对差异：查看校对与同步。

### 备份页

必须提供统一“添加来源”入口和拖拽区域。用户不需要先判断文件或文件夹，后端重新识别类型。

按钮规则：

- 没有来源时不能创建任务。
- `queued` 显示开始。
- `running`、`paused`、`failed_retryable` 显示继续。
- `completed`、`canceled` 不显示开始。
- 继续任务仍需重新输入运行时密码。

### 百度授权页

必须包含：

- 账号表：账号名、UID 摘要、设备摘要、本机标记、token 状态、是否选中。
- 新增授权区：授权 URL、用户码、二维码或二维码文本、轮询状态。
- 验证授权密码区：选择账号、输入授权密码、执行 token 解密验证。

禁止使用 `window.prompt` 获取授权密码。密码字段提交后必须立即清空。

### 恢复页

候选以“备份时选择的来源”为行粒度。文件夹来源恢复到手动目录时，要保留来源根文件夹和内部结构。

必须清楚展示：

- 来源名和来源类型。
- 任务名。
- 文件数和总大小。
- 本地 archive 是否可用。
- 远端 archive 是否确认。
- 阻塞原因。

### 清理页

只展示满足清理门槛的候选。默认清理方式为回收站；隔离目录是备选；永久删除必须在高级区，默认隐藏。

执行清理前必须选中候选行。不能把空选择解释为“全部”。

### 校对与同步页

必须把校对口径写清：

- 来源映射：本地 SQLite 和云端历史导入后的只读视图。
- 远端校对：本地 `remote_objects/upload_sessions` 对比百度 `list/listall`。
- 云端同步：本地 outbox 状态和真实 Cloud Sync summary 回读。

修复动作必须显式确认，不允许自动删除、覆盖或重传远端对象。

## 视觉规范

- 使用中性浅色背景和低饱和强调色。
- 不做营销式首页、hero、大插画、装饰光斑或大面积渐变。
- 页面主体优先使用表格、分区和工具条。
- 卡片只用于独立信息块、重复条目和确认面板。
- 表格紧凑但不拥挤，长文本默认摘要显示。
- 状态颜色固定：成功绿色、警告黄色、失败红色、运行蓝色、禁用灰色。
- 危险动作降权显示，并要求二次确认。

## 文案规范

面向用户的状态文案使用业务语言：

- 待开始
- 运行中
- 已暂停
- 等待重试
- 已完成
- 已取消
- 云端待同步
- 云端已同步
- 远端待校对

避免直接展示内部状态名，除非处于调试或开发诊断区域。

错误消息必须包含：

- 发生在哪个阶段。
- 脱敏原因。
- 用户下一步。

错误消息不得包含：

- Device Token。
- 百度 access token 或 refresh token。
- 授权密码或归档密码。
- wrapping key。
- 完整本地路径。
- 完整远端路径。
- 未脱敏 stdout/stderr。

## 前端安全边界

- 前端不使用 localStorage 或 sessionStorage。
- 前端不持久化密码。
- 动态文本写入 DOM 使用 `textContent` 或安全节点创建 helper。
- 除 `api.js` 外，其他 JS 模块不得直接访问 `window.pywebview.api`。
- 所有写操作必须通过 bridge，并由 Python bridge 串行化。
- 长操作只通过 `operation_id` 轮询状态，不重复触发同一写动作。

## 响应式与可用性

桌面最小窗口尺寸为 1100x720。UI 不针对手机优先设计，但窗口缩小时必须避免文本重叠、按钮挤压和表格不可操作。

必须检查：

- 按钮文案不溢出。
- 表格列可横向滚动或自动摘要。
- Modal 高度过大时可滚动。
- 状态栏和 toast 不遮挡主要操作。

## 设计审计结论

旧文档把 UI 页面、bridge API、DTO、技术约束和实现顺序混在一起，容易让实现者把“页面应该如何工作”和“底层 API 如何实现”混为一谈。新口径中：

- `design.md` 只负责用户体验和前端展示边界。
- `tech.md` 负责 bridge、API、线程、数据和打包技术约束。
- `spec.md` 负责每个功能任务的验收。
